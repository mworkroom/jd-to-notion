# Devlog — Admissions Guideline Helper Phase 1

- Project: Admissions Guideline Helper
- Phase: 1 — Local web app MVP
- Original work date: 2026-06-24
- Log written: 2026-07-09
- Scope: Phase 1 only. Notion integration, Word document generation, and Phase 2 planning are excluded.

## 1. Background

This project started from a recurring admissions-guideline workflow.

The original manual work involved receiving a JANDI request message, extracting the student name, requester, request date, universities, programme names, and programme URLs, then preparing a Word working file and registering related information in Notion.

The first automation idea was n8n. That seemed plausible because the task looked like a classic automation flow: parse text, calculate dates, create Notion records, and generate a file. However, JANDI’s outgoing webhook was not useful in practice because it required messages to start with a slash command such as `/입학요강`. Asking requesters to change their writing habit was unrealistic.

The project direction then shifted from n8n to a local-only web app.

The key realization was that the only unavoidable manual step is copying the JANDI message. Once the text is pasted into a dedicated app, the rest can be handled by code. This makes the web app approach more suitable than n8n for this workflow.

## 2. Phase 1 Goal

Phase 1 was intentionally limited to a safe, local MVP.

The goal was not to connect Notion yet. The goal was to create a local web app that could:

1. run only on the user’s computer,
2. accept a pasted JANDI request message,
3. perform mocked structured extraction,
4. display the extracted data in editable fields,
5. derive the programme label,
6. calculate the deadline,
7. generate the final Word filename,
8. copy the filename with one click,
9. prepare the UI structure for later Notion integration.

The most valuable immediate output was the filename:

```text
[2026입학요강] StudentName님_Programme Label.docx
```

Even before full Word or Notion automation, this reduces one of the highest-friction parts of the task: manually typing long, awkward filenames.

## 3. Why Local Web App

The project was designed as a local-only app instead of a public deployment.

Reasons:

- The app is for one user.
- The workflow always happens on the work computer.
- JANDI request text may contain private student and business information.
- There is no need for other users to access the app.
- A public web app would require authentication and extra security decisions.
- A local app can keep API keys and future Notion credentials out of browser code.

The server is bound to:

```text
127.0.0.1
```

This means the app is only accessible from the same computer.

## 5. Implemented Features

### 5.1 Local server

The app runs through a small Node HTTP server.

Commands:

```powershell
npm test
npm start
```

The app opens at:

```text
http://127.0.0.1:3000
```

The server serves static frontend files and exposes one mocked extraction endpoint:

```text
POST /api/extract
```

### 5.2 JANDI input screen

The first screen accepts one complete JANDI request message.

The user pastes the message and clicks:

```text
Analyze
```

Phase 1 still uses mocked extraction, not the real OpenAI API.

### 5.3 Editable extracted request form

After analysis, the app shows editable fields for:

- requester name,
- request date/time,
- student base name,
- university name,
- programme name,
- programme URL.

The extracted values are not treated as final. The user can correct them before using the output.

### 5.4 Programme rows

The user can add or remove programme rows.

Each programme row includes:

- university name,
- programme name,
- programme URL,
- original university text,
- university alias match status,
- major search key,
- proposed Notion Major name.

This prepares the UI for Phase 2 Notion matching.

### 5.5 Student mode placeholder

The app already includes a UI section for:

```text
New client / Existing client
```

This is not connected to Notion yet. It exists as a Phase 2 placeholder.

### 5.6 Notion preview placeholder

The app shows a preview of what will eventually be matched or created in Notion.

In Phase 1, this is preview-only. The `Create Notion records` button is disabled.

### 5.7 Derived output

The app calculates and displays:

- Work Log title,
- Deadline,
- Category,
- Request season,
- Programme Label,
- Final Word filename.

Current fixed values:

```text
Category = 입학요강
Request season = 2026/27
```

### 5.8 Filename copy

The app generates a final Word filename and provides a one-click copy button.

Example:

```text
[2026입학요강] 테스트학생님_Medical Biotechnology and Business Management (MSc).docx
```

This is the most immediately useful Phase 1 output.

## 6. Business Rules Implemented in Phase 1

### 6.1 Deadline calculation

The deadline is calculated as two weekdays after the request date.

Examples covered by tests:

```text
2026-06-15 Monday    → 2026-06-17 Wednesday
2026-06-18 Thursday  → 2026-06-22 Monday
2026-06-19 Friday    → 2026-06-23 Tuesday
```

Weekends are skipped. Public holidays are not handled in Phase 1.

### 6.2 Student duplicate naming rule

The app includes a rule for future student creation.

If a base name already exists, the next display name uses alphabet suffixes:

```text
중복학생
중복학생 B
중복학생 C
중복학생 D
```

If there is a suffix gap, the app advances past the highest existing suffix rather than filling the gap.

Example:

```text
Existing: 중복학생, 중복학생 B, 중복학생 D
Next: 중복학생 E
```

### 6.3 Degree label normalization for Major matching

The app treats degree labels as removable when creating a comparison key.

These are considered equivalent for searching:

```text
MSc Medical Biotechnology and Business Management
Medical Biotechnology and Business Management MSc
Medical Biotechnology and Business Management (MSc)
Medical Biotechnology and Business Management
```

The comparison key becomes:

```text
medical biotechnology and business management
```

### 6.4 Proposed Notion Major name

When a programme has a leading or parenthesized degree label, the proposed Notion Major name moves the degree label to the end.

Examples:

```text
MSc Biomedical Sciences with Bioenterprise
→ Biomedical Sciences with Bioenterprise MSc

Medical Biotechnology and Business Management (MSc)
→ Medical Biotechnology and Business Management MSc
```

This supports the preferred Notion search format: subject first, degree last.

### 6.5 Programme Label generation

The app compares all programme names.

If a meaningful subject phrase appears in two or more programme names, it uses the shared phrase.

Example:

```text
Biomedical Sciences with Bioenterprise MSc
Biomedical Sciences with Management MSc
→ Biomedical Sciences with
```

If there is no meaningful shared phrase, it falls back to the first programme name.

### 6.6 Word filename generation

The final filename follows:

```text
[2026입학요강] StudentName님_Programme Label.docx
```

Windows-invalid filename characters are removed from the label.

Example:

```text
MSc: Policy / Law * Track
→ MSc Policy Law Track
```

### 6.7 Work Log title rule

The app can calculate the next admissions-guideline task title.

Existing old and numbered titles both count.

Example:

```text
입학요강
입학요강 2
비자
→ 입학요강 3
```

In Phase 1, the UI currently displays the default based on an empty list. Actual Notion-based counting is left for Phase 2.

## 9. Important Design Decisions

### 9.1 No JANDI webhook for Phase 1

JANDI outgoing webhook requires a slash command at the start of the message.

That would require requesters to change their behavior, which is not practical.

The app therefore assumes manual copy and paste from the JANDI desktop app.

### 9.2 No n8n for Phase 1

n8n was considered, but the workflow’s real entry point is still manual copy/paste.

Once copy/paste is accepted, a custom web app gives better control over review, editing, filename generation, and future Notion matching.

### 9.3 Mock extraction first

Phase 1 does not use the OpenAI API yet.

This was intentional. It allows UI, normalization rules, and filename generation to be tested before adding API cost or model variability.

### 9.4 Notion writes are delayed

The app already contains UI placeholders for future Notion work, but write operations are postponed.

This avoids accidentally creating wrong records while matching rules are still being tested.

## 10. Lessons Learned

- A zipped project folder is the most efficient way to pass a local coding project back to ChatGPT for review.
- `.env.example` is a template. The real `.env` should be created locally and never committed.
- For this workflow, a small local web app is more suitable than n8n because the trigger cannot be fully automated from JANDI.
- The biggest immediate value is not full document automation. It is reducing filename and metadata friction.
- Phase-based development works well here: first UI and filename, then read-only Notion matching, then safe writes, then Word generation.

## 11. Phase 1 Outcome

Phase 1 successfully created a local-only admissions-guideline helper app that turns a pasted JANDI request into reviewed structured data and a usable Word filename.

The app is not yet a complete workflow automation tool, but it establishes the foundation for the next stages:

1. read-only Notion matching,
2. controlled Notion record creation,
3. Word template generation,
4. optional real AI extraction.

Phase 1 is therefore complete as an MVP foundation.
